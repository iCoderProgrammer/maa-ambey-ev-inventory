== Behaviour ==
- Idempotency: a DisplayAction (kind, unitId, version, trimmed note, key) is made once per user decision by
  newDisplayAction (crypto.randomUUID, the project's existing key source) and frozen. The hook's variables are the
  action, so mutate(sameAction) resends the same key, path and body; the hook and API function never create a key.
  sendDisplayAction refuses a malformed action (key, version, unit) before any request. Mutations are not retried
  automatically (queryClient: retry false).
- Response: validated with zod; must be the movement type of the action and belong to the requested unit; the
  movement must belong to the returned unit; statuses from the INV-005 enum; quantities 0/1.
- Errors (describeDisplayMoveError): stale-version (VERSION_CONFLICT), invalid-state (INVALID_STATE, server message),
  key-reused (IDEMPOTENCY_KEY_REUSED -> start a new action), signed-out (401), forbidden (403), not-found (404, never
  says whether the unit exists), invalid-input (422 with field details), uncertain (network, 5xx, REQUEST_TIMEOUT ->
  retry the same action; unreadable 2xx -> reload). No failure is described as "nothing happened" when unknown.
  401/403 keep the shared queryClient handling (session ended / permissions re-read).
- Cache: nothing optimistic. On success all vehicle-unit queries (vehicleUnitKeys.all: every list filter/page and
  every detail) are invalidated and refetched; on VERSION_CONFLICT, INVALID_STATE or an unreadable 2xx they are
  refetched too; other failures leave the cache untouched.
- Permission: Permission.VehicleUnitDisplayManage; useStockMovementPerms().manageDisplay is true only when /me lists
  it. No grant added anywhere; no button or screen.
- Not added: movement list/history/timeline query or UI (E-02), PDI/receipt/transfer/reversal calls, any route.
